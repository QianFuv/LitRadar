# 中文技术写作与本地化风格指南

更新日期：2026-09-25\
适用对象：中文技术博客、项目 README、使用文档、科研项目说明，以及相关产品的简体中文界面文案。\
默认语言：简体中文。英文术语、代码和原文引述按各自语境保留。

本指南参考阮一峰《中文技术文档的写作规范》、sparanoid《中文文案排版指北》和 Microsoft《Chinese (Simplified) Localization Style Guide》，并加入适合技术博客和科研项目的编辑约定。它是供作者、编辑和 AI 使用的项目规范，不是三份原文的全文翻译，也不把某一公司的产品约定视为普遍语言规则。

文中标明来源的说明用于追溯依据；关于适用范围、冲突取舍、博客风格、科研报告和 AI 工作流程的规定属于本指南的项目约定。所有改写示例、界面示例和计算示例均用于说明写法，不代表任何项目已经具备相应功能，也不代表真实实验结果。

## 给 AI 的执行摘要

**先保留事实，再改进表达。** 不改变技术含义、实验设定、数据、条件、否定关系和不确定性。不得通过润色补出未核实的功能、测试结果、引用或个人经历。代码、路径、参数、占位符和原文引述不参与普通中文排版替换。

**正文用完整段落承载解释。** 先说清本段的重点，再展开必要的原理、条件或例子。不要一句一段，也不要把自然论述拆成大量小标题和列表。保留必要的长句，但拆开多层嵌套和指代不清的句子。

**按文档类型组织内容。** 技术博客默认采用写在前面、从 `0 -` 开始的主题章节和结语；README、操作手册、论文和界面文案使用各自适合的结构，不套用博客框架。修改既有文章时，保留原有标题体系、元数据和链接路径，除非任务要求调整。

**排版保持一致，但不破坏语义。** 中文与英文、阿拉伯数字之间留一个半角空格；中文标点两侧不补空格；代码和完整英文句子保留原有语法。中文正文默认用中文括号，必要引述用中文弯引号；不为普通概念、举例和强调频繁加引号。

**格式只服务于内容。** 代码块用于需要复制或逐行理解的代码、命令和配置，表格用于真正需要横向比较的数据，列表用于步骤、并列项和检查项。提交前检查事实、结构、术语、排版和可操作性；没有执行过的验证，不得写成已经通过。

## 0 - 适用范围与执行顺序

### 0.1 规则的强度

本指南中的**必须**和**不得**表示交付要求；**默认**和**建议**表示通常采用的做法，可以因文档类型和上下文作出调整；**可以**表示可选处理。正文中的示例不是要求照抄的固定话术。

规则冲突时，首先保护事实、技术语义和机器可读语法，其次满足适用的投稿模板、产品规范及任务的明确要求，再应用本指南。不能为了格式整齐改错代码，也不能为了语言肯定而删去必要的否定和限制。

### 0.2 不统一处理的内容

本指南主要约束中文叙述层。程序代码、配置键名、命令行参数、数学表达式、接口字段、实际路径、直接引文和法定名称，按其自身规则处理。

处理第三方产品文档时，界面名称必须与对应版本的真实界面一致。执行正式 Microsoft 本地化项目时，以该项目提供的术语库、样式要求和资源文件约束为准，不用本指南的通用取舍覆盖客户要求。

## 1 - 先确定读者和文档任务

**写作前明确读者需要完成什么。** 同一个工具的项目介绍、安装教程、原理分析和实验复现说明，应提供不同的信息。项目介绍回答用途和边界，教程帮助完成任务，原理分析解释机制和取舍，复现说明交代输入、环境、流程与结果验证。

默认读者有一般计算机使用能力，但不假定读者熟悉当前项目的内部实现。只解释理解当前任务所必需的术语；不要从与主题无关的基础知识讲起，也不要把关键前提藏在外部链接里。

开头尽快交代实际问题、本文处理的范围和必要背景。避免从时代发展、技术浪潮等泛泛背景开始，也不要先堆产品形容词，再让读者寻找用途。

**项目介绍示例：** 文献检索项目可以先交代目标文献分散在哪里、现有检索流程有什么重复工作，再说明项目覆盖的环节。若仅实现了元数据检索，就不要写成能够完成全文阅读和研究结论验证。

## 2 - 标题与章节组织

### 2.1 通用标题规则

标题层级不能跳跃；上下级标题不重复表达同一主题；没有必要时，不再拆出只有一个子项的层级。这些原则参考阮一峰的标题规范。[R-title]

本指南默认使用一个文档主标题，正文主要使用二级和三级标题。只有篇幅和信息结构确实需要时才使用四级标题，不用增加层级的方式解决段落衔接问题。博客主题已经从元数据生成主标题时，不在正文重复生成同名主标题。

标题应能帮助读者定位内容，例如依赖管理、更新数据、验证运行结果。避免连续使用关于、浅谈、进一步思考等不能区分章节内容的词语。全文题目可以采用谈某某的个人博客形式，但章节仍应说明具体主题。

标题通常不加句末标点。只有真正以问题为主题时才保留问号，不把所有标题都写成模拟提问。并列标题尽量处于同一逻辑层次，不把操作步骤、产品优点和研究结论并列成同级目录。

### 2.2 技术博客的默认结构

技术博客采用以下骨架，但主题名称和章节数量随内容变化：

```markdown
# 谈某个具体问题

## 写在前面

## 0 - 问题与基本原理

## 1 - 主要流程

## 2 - 实际使用中的取舍

## 结语
```

写在前面交代写作缘由、实际问题和适用范围，不承担全文摘要的所有功能。主体按读者理解或操作的顺序展开，不必每节都套用定义、功能、优点、总结的相同结构。

结语回到适用场景、已经解决的问题和仍存在的限制，不逐条复述所有小节，也不使用与正文无关的抒情结尾。篇幅很短的说明不必强行补齐整个骨架。

这一标题形式是本指南的博客约定，不是三份参考资料共同要求的编号规则。

### 2.3 其他文档的结构

README 应让读者较快找到项目用途、适用条件、最小使用流程和进一步文档。使用手册可将基础操作、参考信息和故障排查分开，避免把所有内容塞进一篇长文；这种分层思路参考阮一峰的文档体系规范。[R-structure]

科研文档按研究问题、数据与方法、验证流程、结果和限制组织；具体章节服从研究任务或投稿要求。界面文案按页面和交互状态组织，不使用文章式引言与结语。

## 3 - 段落、句子与语气

### 3.1 让段落围绕一个中心展开

一个段落围绕一个中心组织，段首优先交代重点，段间以空行分隔，Markdown 正文不做首行空格缩进。这些做法参考阮一峰的段落规范。[R-paragraph]

本指南不把屏幕上的四行、七行或固定字数作为段落合格标准。编辑时判断的是主题是否统一、推理是否完整，以及读者是否需要在同一段里记住过多条件。

解释、依据和紧接着的例子可以放在同一段，不要为了制造节奏而拆开。另一方面，问题已经从安装切换到权限，或从方法切换到结果时，就应另起一段。

**不推荐：** 将同一解释连续拆成以下三个独立段落：这个设置控制缓存。它不影响原始文件。删除缓存后需要重新构建。

**推荐：** 这个设置只控制缓存，不影响原始文件。删除缓存后，程序需要重新构建索引，因此首次查询可能需要更长时间。

### 3.2 句子清楚，而不是机械变短

优先使用清晰的主谓结构，减少叠加修饰、模糊代词和没有实际作用的名词化表达。可直接写读取数据，不必写进行数据读取操作；可以写删除记录，不必写对记录实施删除。这一方向与阮一峰的文本规范一致。[R-text]

长句并非一律有问题。包含必要条件、因果关系和适用范围的句子可以保留，但不应把多层例外都挤在一个逗号链中。删减时先移除冗余，再考虑拆句，不得为了缩短句子丢失限定。

其、该方法、这一结果等表达必须有明确指向。一个段落出现多个模型、数据集或阶段时，宁可重复具体名称，也不要让读者猜测代词指向。

建议优先使用主动表达，但当执行者未知、不重要，或研究对象应置于句首时，可以使用被动结构。对禁止事项直接写不得或不能，不必强行改成肯定句。

### 3.3 专业，但不生硬

Microsoft 指南强调根据受众和语境选择表达，而不是逐词照搬英文。[M-pdf] 本指南据此采用专业、自然、克制的正文语气，不照搬营销文案的热情，也不把正式理解为公文式表达。

技术博客可以使用我来说明真实的选择和经历；项目文档通常直接说明操作和系统行为；研究报告按学科惯例使用本文、本研究或具体方法名称。不得为增强亲切感编造亲身测试、踩坑经历或团队共识。

少用显而易见、众所周知、非常简单、只需轻松几步等表述，不预设读者已经理解，也不把任务失败归咎于读者。赋能、颠覆、革命性、一站式等词不能代替具体功能和证据。

不得用按照要求进行了优化、下面给出一个清晰的版本等编辑过程说明占用正文。文章本身应直接进入主题。

## 4 - 术语、名称与中英文表达

**同一概念使用稳定的称谓，不同概念保留差别。** 不要为了避免重复，将精确率、召回率和准确率轮换称为准确性；也不要将原生功能、插件功能和计划功能统一写成支持。

首次出现且影响理解的术语，可以使用中文名称（英文名称，缩写）的形式。后文选用一种主要称谓，不反复附加完整释义。目标读者已经熟悉的缩写可以直接使用，但不得自造缩写以压缩文字。

专有名称遵循其正式拼写和大小写，例如 GitHub、Microsoft。品牌名不是普通标题，不应用英文标题首字母大写规则随意改写。《中文文案排版指北》对此有明确要求。[C]

代码中的标识符与正文中的概念名称分开处理。说到一个接口字段时写 `user_id`，说到它的含义时可以写用户标识；不得把字段改写为中文以追求本地化，也不得擅自把英文标识符变成单数形式。

翻译要保留逻辑强度。可能、建议、必须、尚未和不支持不能互换。面对多义词，应根据产品、代码或论文上下文确定译法，不能只凭词典的第一个义项决定。

## 5 - 中英文混排与空格

本指南选择统一的手工空格规则：中文与英文、阿拉伯数字相邻时，留一个半角空格；中文全角标点与相邻内容之间不另加空格；数字与通常的拉丁字母单位之间留空格。该选择主要参考《中文文案排版指北》。[C]

**示例：** 使用 Python 处理 128 条记录，结果保存在 `results.csv` 中。内存限制为 32 GB，运行时间为 5 s。

百分号与数字连写，例如 80%；角度写作 90°。本指南将温度写作 25 °C，不把角度符号的连写习惯机械推广到所有带有度符号的单位。代码、数学排版或投稿模板另有要求时，使用对应规则。

中文括号和标点前不补空格，例如应用程序编程接口（API）、结果为 80%。不要写成 `API ，` 或 `（ API ）`。

行内代码、链接和加粗文本，按渲染后的相邻文字决定空格。中文链接与中文正文相接时，不因它是链接而额外加空格；英文链接与中文正文相接时，按中英文混排规则处理。

**空格规则不能修改对象内部。** 不拆开正式产品名，不改 URL、邮箱、文件路径、版本号、标识符、命令参数或原文引述中的空格。原始日志按原样展示，解释写在日志之外。

## 6 - 标点、引号与强调

### 6.1 按语言和用途选择标点

中文叙述采用中文标点；完整英文句子、代码和机器可读内容保留相应标点。中文句子里的并列项使用顿号，说明性补充默认使用中文括号。这些原则参考阮一峰的标点规范。[R-marks]

正文中的括号默认写成缓存文件（可删除）、应用程序编程接口（API）。公式和代码中的圆括号不变，例如 `f(x)`；时间中的冒号也不变，例如 09:30。

句内补充说明位于句末时，句号放在括号之后。独立成句的整段括注可保留其自身标点，不把所有括注都用同一替换规则处理。

### 6.2 引号只承担必要功能

必要引述使用中文弯引号，嵌套时外层用双引号、内层用单引号。直角引号不是本指南的默认形式；《中文文案排版指北》也将这项选择放在争议部分，而非必选规则中。[C]

不为功能名称、一般概念、比喻和示例中的关键词习惯性加引号。概念需要解释，就解释含义；需要表示代码字面量，就使用行内代码。不能靠引号暗示一个未定义的术语。

中文作品名使用书名号。保留英文原名的作品可按原文或引用格式处理；正式参考文献表服从所选引用格式。软件名、按钮名和文件名不因名称较长就使用书名号。

### 6.3 少用装饰性符号

正文尽量不用破折号串联解释，不用连续感叹号、连续问号和大量省略号制造语气。需要补充条件时优先使用完整句、逗号、冒号或括号。

数值范围优先写至，例如 3 至 5 次、10% 至 15%。代码、日期、文件名和图表编号中的连接符保留，不把 `2026-09-25` 或 `--help` 当成需要清理的破折号。

正文确需省略号时统一使用 `……`，但代码、日志和直接引文中的省略记号按原样处理。

### 6.4 强调用于帮助定位

加粗只标记关键结论、重要限制和需要定位的界面标签，不整段加粗，也不让每一段都以相同形式开头。连续几段都需要强调时，应先检查结构是否清楚。

中文正文不依靠斜体表达长篇强调。代码、路径和参数用行内代码；界面标签默认用加粗，例如选择 **设置**，再打开 **数据源**。这一界面标记方式是本指南的项目约定。

## 7 - 数字、单位、日期与计算表达

### 7.1 数字必须有明确口径

数量、参数、测量值和版本使用半角阿拉伯数字；第一步、两种方式等自然表达可以使用中文数字，不强行数字化。大数是否使用千位分隔、如何描述范围和增减，参考阮一峰的数值规范。[R-number]

本指南默认在展示五位及以上整数时使用千位分隔，例如 12,800；四位数字在同一组数据中保持一致。年份、编号、端口号、代码和机器读取的数据不插入千位分隔符。

单位必须匹配实际测量对象。涉及存储容量时，注明数据使用的计量口径；不得未经核实便将 GB 改成 GiB，或把不同大小写的单位当作等价写法。表格可以把共同单位放入列名，正文应在不引起歧义的前提下减少重复。

小数位数与数据精度匹配。不要凭空补出精度，也不要为了全篇统一位数而掩盖重要差异。原始结果和四舍五入后的展示值需要能对应。

### 7.2 区分差值、相对变化和倍数

减少到和减少了表达不同含义；不要使用减少几倍这种容易混淆的写法。[R-number] 本指南要求在结果比较中交代起点、终点和计算对象。

**百分比示例：** 某指标从 80% 升至 84%，提高了 4 个百分点，相对提高 5%。不能只写提高了 4%，也不能省略比较基准。

**性能示例：** 完成相同工作所需时间从 20 s 降至 5 s，可以写耗时减少 75%，或原耗时是现耗时的 4 倍。只有明确比较的是相同工作量下的处理速度时，才进一步说明相应速度比，避免把耗时变化和吞吐量变化混为一谈。

计算相关内容应让读者看见输入、计算关系和结果。简单计算可以写在正文中，不为每次四则运算单独放置代码块。

### 7.3 日期与时间

正文默认写 2026 年 9 月 25 日；元数据、文件名和需要排序的记录默认写 `2026-09-25`。同类字段保持一致，避免使用月、日顺序不明确的缩写。

需要精确定位时间时写完整日期和时间。跨地区协作、定时任务和日志比较必须说明时区，例如北京时间 2026 年 9 月 25 日 09:00（UTC+8）。可复现记录不单独使用今天、昨晚或最近。

日期、时间、时区和元数据约定是本指南的补充规则。

## 8 - Markdown、代码与示例

### 8.1 正文优先，格式按用途选择

解释原理、讨论取舍和串联论证时使用段落。步骤确实有先后顺序时使用有序列表；彼此独立的检查项可以使用无序列表。同一列表内保持条目层次和句式协调，但不为了整齐删去必要信息。

完整句子的条目加句末标点；短语式条目可以不加。同一组条目不要随意混用。只有一个信息点时，通常直接写成正文。

表格只用于需要横向查阅的参数、指标或差异，不把长篇解释装进单元格。内容主要是因果关系或需要多层限定时，用段落通常更合适。列表和表格不设强制数量，但必须比正文更便于理解。

### 8.2 代码块必须有使用价值

需要复制执行、检查缩进或理解多行逻辑的内容才放入代码块，并标明正确的语言类型。只是提到文件名、参数或一条短命令时，优先使用行内代码，例如 `config.yaml`、`--help`。

代码块之前交代用途、运行位置和必要前提，之后解释预期结果或验证方式。连续步骤可以合并为一个连贯示例，不为每一条命令制造一个小标题和独立代码块。

可复制代码不得混入终端提示符、聊天说明、假输出或未经说明的省略部分。输入与输出分开；没有实际执行的输出不得伪装成运行记录。示例中的替换项需要明确说明，不使用真实密钥、私人路径或个人敏感数据。

面向图形界面使用者时，优先解释具体任务和可见操作；命令行用于确有必要的配置、自动化和复现。不要仅因作者熟悉命令行，就把科研协作教程写成命令清单。

### 8.3 说明性示例与实测结果分开

示例应具有足够上下文，让读者知道输入是什么、发生了什么，以及为什么能说明当前概念。用于讲解的虚构数字必须标明示例，不与实际数据放在同一叙述层。

只验证了局部功能，就写明验证范围。代码能运行、示例能复现和方法能推广，是不同层次的结论，不得相互替代。

## 9 - 来源、链接与时效性

**可核查的技术结论应有可定位的依据。** 功能状态、版本支持、性能比较、实验结论、政策和授权范围，应指向相应文档、发布记录、代码、论文或原始材料。不要仅凭搜索摘要或没有阅读的链接编写详细结论。

事实、推断和建议分别表达。官方文档记载的能力可以写文档说明；根据材料作出的推测写可能或据此推测；个人选择写在这些条件下建议。不得把暂未找到证据改写为功能一定不存在。

链接文字说明目标内容，例如安装说明、数据格式规范，不使用大量点击这里。与判断直接相关的来源放在对应论述附近；较长文章可以另设参考资料，但不能只堆一组与具体结论无法对应的链接。

易变化的信息注明适用版本、测试环境或核查日期。引用某次测试时交代比较条件，不把他人的宣传口径写成自己的实测结果。无法读取来源全文时说明限制，不补造页码、作者、发布日期或 DOI。

直接引用保持原文措辞并标明来源；解释和翻译与引文区分。普通润色不改写引文中的错别字和特殊标点，需要提示时在引文之外说明。

本节是面向技术博客与科研写作的补充规则。

## 10 - 图表与科研结果说明

### 10.1 图表应当能够独立理解

每幅承担信息表达的图应有说明对象的图题，正文解释读图所需的变量、单位和关键发现。没有图也能用一句话说清的内容，不必为了图文并茂重复作图。

Markdown 图片提供有意义的替代文本，不能只写图片或截图。不仅依靠颜色表达分组和重要程度；操作说明同时给出控件名称，避免只说点击右侧红色按钮。

引用他人图表标明来源；自行重绘也说明数据来源。修改坐标范围、单位、基准或分组口径时应明确交代，避免让展示方式改变读者对结果大小的理解。

### 10.2 研究报告保留实验边界

报告至少应让读者知道研究问题、数据来源和划分方式、比较对象、核心设定、评价指标以及结论适用范围。根据研究类型交代随机种子、运行次数、预算或计算环境，不把并不适用的项目强行补齐。

指标首次出现时说明计算对象、正负方向和必要口径。分类任务需要区分总体指标与某一类别指标；预算受限任务需要区分训练成本、单次运行成本和评估成本。图表和正文采用一致的统计范围。

报告均值、波动范围或置信区间时，说明统计单位和计算方法。只给出观察值差异时，不擅自使用统计显著；只在一种数据划分或配置下验证时，不写成普遍优越。

代理指标的改善不自动等于业务效果改善。研究限制应指出具体受限环节及其影响，而不是只在结尾补一句仍有不足。

本节是科研项目文档的补充约定，不是对三份参考指南中统计规则的转述。

## 11 - 界面文案与本地化

### 11.1 界面文案与文章正文分开管理

Microsoft 指南区分软件本地化和文档本地化，并对部分标点采用不同处理方式。[M-pdf] 本指南不将这些产品约定一概推广：普通中文文档采用本指南的正文规则；第三方产品界面按其产品规范；自主项目在没有既有约束时，默认沿用本指南的中文标点和术语。

按钮、字段标签和状态提示无需写成完整解释段落，例如导入文件、正在索引。需要说明条件或后果时，使用完整的辅助说明，不靠缩短标签隐藏重要限制。

本地化不能只对照孤立字符串。应确认文字所在页面、触发时机、实际控件、前后状态和动态替换内容。Microsoft 指南特别提醒检查占位符将被替换成什么。[M-pdf]

### 11.2 文案说明操作及其后果

按钮名称尽量说明具体动作，例如保存设置、导出结果，而不是在所有对话框里重复使用确定。删除、覆盖、发送等操作，应在确认界面说明对象和后果；只有确实可恢复时才承诺可以恢复。

错误信息先说明哪项操作未完成，再提供已知且有效的处理方式。原因尚未确定时不要写成已经查明，也不要默认要求重启、清除数据或重新安装。

**已知原因示例：** 导入失败。文件缺少 `title` 列，请补充后重试。

**原因未知示例：** 暂时无法完成导入，请稍后重试。问题持续出现时，请提供错误编号以便排查。

状态提示必须对应真实完成的阶段。文件上传成功不等于导入成功，提交任务不等于任务完成，生成结果不等于结果已验证。具体措辞按项目实际流程选择。

### 11.3 保留不可翻译的技术结构

占位符、格式说明符、变量名、转义序列、资源键和有语义作用的标签必须保持有效。允许调整自然语言语序，但不得随意改名、增删或重排依赖位置的参数。是否可以重排，取决于实际格式化机制。

例如 `已导入 {count} 篇文献。` 中的 `{count}` 是占位符，不应翻译成 `{数量}`，除非任务同时要求并正确修改资源绑定。替换完成后，还需要检查空格、量词、标点和语句是否自然。

本小节的具体检查流程属于本指南的实现约定。它不授权编辑者调整项目代码或资源结构。

## 12 - 文件、元数据与维护

代码仓库中的新增文档路径默认使用简短的英文小写词和连字符，例如 `getting-started.md`。约定俗成的说明文件保留其形式，例如 `README.md`、`LICENSE` 和本文件 `STYLE_GUIDE.md`。这一默认习惯参考阮一峰的文件命名规范。[R-structure]

不把英文文件名规则扩大为所有场景的禁令。面向中文读者交付的独立报告可以使用清楚的中文文件名；维护已有项目时，不得为统一风格擅自重命名文件、改变发布路径或破坏引用。

文章元数据保持字段含义稳定。原始发布日期不因润色而改成今天；完成实质更新后，根据博客约定维护 `updated`。摘要应随内容变化复核，不能保留已经不准确的功能和性能描述。

修改内容时同时检查目录、锚点、相对链接、图片路径和示例文件名。记录真正完成的修改和验证，不能仅修改日期制造内容已经重新核实的印象。

## 13 - 三份指南的冲突与本指南的取舍

本节用于解释边界，具体执行仍按前文，不另设一套互相竞争的规则。

**中文与数字之间的空格。** 阮一峰允许有空格或无空格，但要求一致；《中文文案排版指北》主张加空格。本指南统一加空格，以减少编辑时的自由选择。[R-text][C]

**句子和段落长度。** 阮一峰给出了字数、行数限制。本指南保留控制阅读负担的目的，但不照搬固定阈值，也不将短句理解为一句一段。[R-text][R-paragraph]

**语气与完整性。** 阮一峰偏向正式技术说明，Microsoft 指南强调适合受众的自然表达。本指南要求自然且准确；博客和研究正文保留完整论述，界面标签按功能采用短语，不把界面中的省略式表达扩展到整篇文章。[R-text][M-pdf]

**引号和括号。** 《中文文案排版指北》对直角引号的偏好是可选项；Microsoft 文档中的括号还区分括号内字符。本指南的普通中文正文统一使用中文弯引号和中文括号，代码、英文原文及正式产品要求除外。[C][M-pdf]

**链接与文件名。** 不因文本成为链接就额外添加空格；英文文件名是代码仓库的默认选择，不是对所有中文交付物的禁令。这些是对原指南中可选偏好及较强约束的项目化调整。[C][R-structure]

**字体、界面标记和品牌规则。** 不将 Microsoft 特定工作流程中的字体、标签及品牌处理要求作为通用 Markdown 标准。本指南使用正文、标题、行内代码和少量加粗表达信息层次；承接对应产品项目时恢复该产品的具体要求。

**博客结构和科研规范。** 写在前面、`0 -` 编号章节、结语，以及科研结果、证据等级和 AI 交付检查，均属于本指南的补充约定，不归为三份原文的共同结论。

## 14 - AI 写作与编辑流程

### 14.1 开始前

先判断任务是写作、润色、翻译、摘要还是事实核查，并确定文档类型。已有文档应先阅读相关内容，再决定修改范围；摘要需要足够完整的源材料，不能把局部摘录当作全文。

建立不可随意改变的内容清单，包括技术名词、代码、数字、单位、版本、研究设定、限制条件、引用和已有元数据。信息不足且影响正确性时，明确标注待核实事项或提出必要问题，不编造答案。

### 14.2 编辑时

先修复事实冲突、缺失前提和结构问题，再改句子、术语及排版。优先做能够明显改善理解的修改，不为显示工作量而全面重写已经自然准确的段落。

根据任务权限处理问题。只要求排版时，不擅自更新技术路线；只要求翻译时，不补入自己的结论；只要求润色时，遇到疑似事实错误应提出说明，而不是悄悄改成另一个未经核实的说法。

不得仅凭正则替换处理整份文档。批量处理空格和标点时，保护代码块、行内代码、链接目标、数学内容、元数据与直接引文，之后复核边界处的呈现。

### 14.3 交付前检查

- **事实与范围：** 数字、技术含义、条件和证据强度没有被改写；新增事实有依据，未验证内容没有伪装成实测。
- **结构与行文：** 标题便于定位，段落围绕中心展开，没有一句一段、重复结语或机械套用的章节。
- **术语与格式：** 名称、大小写、空格、标点、数字和单位一致，代码与占位符未被破坏。
- **可操作性：** 必要前提、路径、输入、步骤和验证方式足够明确，危险或不可逆后果没有被省略。
- **维护信息：** 引用、链接、图片、目录和元数据与当前内容一致，日期更新不暗示未经执行的核查。

完成检查后直接交付正文或文件。只有确实存在重要改动、未决事实或验证限制时，附上必要说明；不追加固定的自我评价和与任务无关的后续服务建议。
